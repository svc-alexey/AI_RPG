# Implementation Plan: Следующие этапы после MVP-ядра

## 1. Цель документа

Зафиксировать оставшиеся этапы реализации после сборки базового MVP.
Этот план не заменяет `Plan.md`, а продолжает его.

Правило ведения документа:
- каждая задача оформляется как чекбокс
- при выполнении задачи чекбокс переключается в `[x]`
- невыполненные задачи остаются в состоянии `[ ]`
- каждая новая feature-задача, если это не bugfix, получает отдельную папку в `docs/features/<feature-slug>/`
- каждая новая feature-задача одновременно регистрируется в `docs/features/CATALOG.md`
- feature-папка создается по шаблону из `docs/features/_template/`
- реализация новой фичи начинается только после `01-Architecture.md` и `02-PRD.md`
- каждый ролевой этап новой фичи ведется в отдельном окне или треде

## 2. Текущее состояние

Уже реализовано:

- [x] Flutter desktop-first каркас
- [x] Базовые экраны: `Home`, `New Game`, `Chat`, `Settings`, `Saves`
- [x] Создание кампании и стартовый `CampaignState`

## 3. Этап 1. Полная локализация `ru/en`

Цель:
Перевести проект с хардкоженных строк на полноценную систему локализации с двумя языковыми состояниями.

Задачи:

- [ ] Ввести единый localization layer для UI-строк
- [ ] Вынести все пользовательские тексты из экранов и сервисов
- [ ] Сделать два полных языковых состояния: `ru` и `en`
- [ ] Добавить переключатель языка в приложение
- [ ] Связать выбранный язык с AI-слоем
- [ ] Проверить, что приложение по умолчанию стартует на русском

Результат этапа:

- [ ] Все пользовательские строки управляются централизованно
- [ ] Переключение языка влияет на весь пользовательский опыт
- [ ] Код не зависит от строк, записанных прямо в виджетах

## 4. Этап 2. Ускорение ответов модели через `/no_think`

Цель:
Сократить время ответа локальной модели LM Studio за счет prompt-режима `/no_think` или аналогичного быстрого режима, если модель его поддерживает.

Задачи:

- [x] Проверить, как текущая модель LM Studio реагирует на инструкцию `/no_think`
- [x] Зафиксировать безопасный prompt-шаблон для быстрого ответа без длинного рассуждения
- [x] Встроить этот режим в AI-слой приложения для игровых ходов
- [x] Убедиться, что формат JSON-ответа и структура хода не ломаются
- [x] Добавить fallback на обычный prompt, если `/no_think` не поддерживается конкретной моделью
- [x] Проверить субъективное и техническое ускорение ответа на локальной модели

Результат этапа:

- [x] Игровые ответы приходят быстрее на совместимых локальных моделях
- [x] Приложение не зависит жестко от одной модели или одного prompt-хинта
- [x] Быстрый режим не ломает контракт AI-ответа

## 5. Этап 3. Summary и память кампании

Цель:
Сделать минимальную, но полезную систему памяти истории вместо одного упрощенного `summary`.

Задачи:

- [ ] Добавить rolling summary последних ходов
- [ ] Отделить краткую сводку кампании от последних событий
- [ ] Отдельно хранить текущую активную цель
- [ ] Обновлять summary после каждого завершенного хода
- [ ] Отображать summary в UI как отдельный полезный блок
- [ ] Подготовить структуру данных для будущего расширения памяти

Результат этапа:

- [ ] Длинная кампания остается понятной после паузы и загрузки save
- [ ] AI получает более стабильный контекст
- [ ] История меньше разваливается на длинной сессии
