# Правила Flutter для проекта

## 1. Архитектура
1. Использовать feature-first структуру: `lib/src/features/<feature>/...`.
2. Разделять слои: `presentation`, `application`, `domain`, `data`.
3. `domain` не зависит от Flutter/UI и внешних SDK.
4. Любой вызов AI/API идет через gateway/репозиторий, а не напрямую из UI.

## 2. Состояние и UI
1. Виджеты должны быть максимально dumb, бизнес-логика в state/controller/use-case.
2. Не хранить долгоживущую бизнес-логику в `StatefulWidget`.
3. Любой асинхронный код из UI проверяет `mounted`.
4. `BuildContext` не использовать после `await` без явной проверки.

## 3. Модели и сериализация
1. DTO и доменные сущности разделять.
2. Все сохраняемые сущности версионировать через `schemaVersion`.
3. JSON-ключи и контракты API менять только через обратную совместимость.
4. Ручные `Map<String, dynamic>` в бизнес-слое не использовать, только typed-модели.

## 4. Ошибки и логирование
1. Запрещен `print`, использовать централизованный logger.
2. Ошибки сети/валидации/парсинга оборачивать в типизированные failure-классы.
3. UI не должен показывать raw-тексты исключений.

## 5. Производительность
1. Избегать лишних rebuild: выносить части UI в отдельные виджеты.
2. Для длинных списков использовать `ListView.builder`/`SliverList`.
3. Тяжелые операции (парсинг, компрессия, агрегация) выносить из main isolate.
4. Не хранить крупные JSON-объекты в состоянии экрана без необходимости.

## 6. Тестирование
1. Обязательны unit-тесты для use-case и валидатора состояния.
2. Widget-тесты для ключевых экранов: setup, game loop, save/load.
3. Контрактные тесты AI gateway на стабильный JSON-формат ответов.
4. Регресс-тесты миграций локального хранилища.

## 7. Код-стайл и качество
1. Соблюдать правила из `analysis_options.yaml`.
2. Перед merge: `flutter analyze` и `flutter test` без предупреждений и падений.
3. Один pull request не должен смешивать архитектурный рефакторинг и новую фичу.
4. Любое изменение контракта данных сопровождается обновлением документации.

## 8. Правила для AI RPG домена
1. AI-ответ всегда считать недоверенным до прохождения валидатора.
2. Источник истины: состояние движка, не текст повествования.
3. Валидация последствий обязательна до сохранения хода.
4. Память кампании собирать слоями: recent turns + summary + entity cards + world canon.
