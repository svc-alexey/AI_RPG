# Правила Flutter для проекта

## 1. Архитектура

1. Использовать feature-first структуру: `lib/src/features/<feature>/...`.
2. Не смешивать UI и доменную логику без необходимости.
3. Вызовы AI/API не идут напрямую из случайного UI-кода без сервисного слоя.

## 2. Состояние и UI

1. Виджеты должны быть максимально простыми, бизнес-логика живет в сервисах и orchestration-слое.
2. Любой асинхронный код из UI обязан проверять `mounted`.
3. `BuildContext` после `await` использовать только осторожно и осознанно.

## 3. Модели и сериализация

1. Сериализуемые сущности должны иметь стабильную схему.
2. Изменения формата save требуют продуманной совместимости.
3. Typed модели предпочтительнее ручных неструктурированных map.

## 4. Ошибки и надежность

1. AI-ответ всегда считать недоверенным до валидации.
2. UI не должен показывать сырой stack trace пользователю.
3. Ошибка AI не должна приводить к порче кампании.

## 5. Производительность

1. Избегать лишних rebuild.
2. Для длинных списков использовать builder-подход.
3. Не передавать в UI лишний тяжелый JSON-контекст без необходимости.

## 6. Тестирование

1. Перед merge обязательны `flutter analyze` и `flutter test`.
2. Ключевые user flow должны быть покрыты хотя бы smoke/widget проверками.
3. Изменения AI-контракта требуют проверки structured response handling.

## 7. Качество

1. Соблюдать правила из `analysis_options.yaml`.
2. Не смешивать большие рефакторинги и новую фичу без явной причины.
3. При изменении контрактов обновлять документацию.
