# AI_PRG: Единый контекст проекта

## 1. Назначение документа
Этот файл фиксирует стабильный контекст для SpecKit, чтобы агент не терял:
1. Общие продуктовые цели.
2. Архитектурные правила.
3. Технические ограничения.
4. Источники истины по требованиям и данным.

## 2. Продукт в одном абзаце
AI_PRG - narrative RPG-платформа на Flutter, где AI генерирует историю и варианты последствий, а детерминированный движок валидирует и применяет только допустимые изменения состояния. Поддерживаются разные AI-провайдеры, включая LM Studio, локальные сохранения, короткие и длинные кампании и многослойная память для длинных игровых сессий.

## 3. Источники истины
1. Конституция проекта: `.specify/memory/constitution.md`
2. Product requirements: `PRD.md`
3. Архитектура: `Architecture.md`
4. JSON-модели сущностей: `entities.models.json`
5. Flutter инженерные правила: `FlutterRules.md`
6. Analyzer/lint конфигурация: `analysis_options.yaml`
7. Стратегический и implementation-план: `Plan.md`, `ImplementationPlan.md`
8. Единый каталог фич: `docs/features/CATALOG.md`
9. Протокол команд и окон: `docs/features/COMMANDS.md`

## 4. Инварианты домена
1. AI output недоверенный до валидации.
2. Состояние мира, инвентаря и квестов меняется только через движок.
3. Любой ход должен быть воспроизводим из лога и снимка состояния.
4. Save/load обязаны быть обратно совместимы в пределах минорной версии схемы.

## 5. Технологический профиль
1. Клиент: Flutter, desktop-first.
2. Lint/quality: `flutter_lints` и усиленные analyzer rules.
3. AI-layer: provider-agnostic gateway и адаптеры.
4. Локальный AI-режим: LM Studio через OpenAI-compatible API.

## 6. Обязательная синхронизация документов
1. При изменении требований обновляется `PRD.md`.
2. При изменении модулей обновляется `Architecture.md`.
3. При изменении сущностей и контрактов обновляется `entities.models.json`.
4. При изменении инженерных правил обновляются `FlutterRules.md` и `analysis_options.yaml`.
5. При изменении базовых принципов обновляется `.specify/memory/constitution.md`.

## 7. Feature-пакеты
1. Каждая новая фича, если это не bugfix, должна иметь отдельную папку в `docs/features/<feature-slug>/`.
2. Feature-пакет создается по шаблону из `docs/features/_template/`.
3. Каждая новая фича должна одновременно регистрироваться в `docs/features/CATALOG.md`, чтобы попадать в общий scope проекта.
4. Перед реализацией фичи внутри пакета должны быть заполнены:
   - `01-Architecture.md`
   - `02-PRD.md`
5. Во время работы допускается, что одна фича реализуется, а другие параллельно проходят архитектуру и аналитику.
6. Каждый ролевой этап новой фичи должен вестись в отдельном окне или треде, чтобы архитектор, аналитик, разработчик и тестировщик не смешивали контекст.

## 8. Локализация как инвариант продукта
1. Приложение должно по умолчанию запускаться на русском языке.
2. Приложение обязано поддерживать два полных языковых состояния: `ru` и `en`.
3. Переключение языка должно менять весь пользовательский опыт целиком:
   - интерфейс
   - кнопки и подписи
   - ошибки и служебные статусы
   - стартовые игровые тексты
   - AI-промпты и ожидаемый язык ответа модели
4. Новая фича считается незавершенной, если она реализована только для одного из двух поддерживаемых языков.
