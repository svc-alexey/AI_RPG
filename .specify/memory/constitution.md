# AI_PRG Constitution

## Core Principles

### I. Engine-First Source of Truth
LLM никогда не является источником истины состояния игры.
Источник истины только один: детерминированный игровой движок и сохраненное состояние.

### II. Structured AI Contracts Only
Все AI-интеграции работают через единый gateway и строгий JSON-контракт.
Свободный текст без структуры не используется для изменения состояния.

### III. Layered Memory for Coherence
Память кампании строится слоями:
1. Recent turns
2. Rolling summary
3. Entity cards
4. World canon

### IV. Flutter Architecture Discipline
Клиент строится по feature-first структуре с разделением слоев:
`presentation -> application -> domain -> data`.

### V. Quality Gates Before Merge
Перед merge обязательны:
1. `flutter analyze` без критичных ошибок
2. `flutter test` без падений
3. Тесты и валидация для доменных изменений
4. Обновление документации при изменении схем и правил

## Development Workflow
1. Любая новая фича проходит цепочку `specify -> plan -> tasks -> implement`.
2. Изменение контрактов данных требует плана миграции и фиксации версии.
3. Для долго живущих фич обязательна проверка на совместимость save/load.

## Feature Delivery Order
1. Для любой новой фичи, если это не исправление ошибки, обязателен фиксированный порядок этапов:
   - архитектурный анализ и план
   - аналитический этап с PRD или feature-spec
   - разработка
   - тестирование
2. Для bugfix-задач допускается сокращенный поток, если изменение локальное и не меняет архитектуру или требования.
3. Эта последовательность обязательна, а не рекомендательна.

## Planning Traceability
1. Если создается отдельный implementation plan, он должен вестись как checklist.
2. Выполненные задачи должны отмечаться чекбоксами прямо в плане.
3. План должен оставаться актуальным и отражать реальный статус работы.

## Feature Packet Workflow
1. Каждая новая фича, если это не bugfix, обязана иметь отдельный feature packet в `docs/features/<feature-slug>/`.
2. Feature packet создается по единому шаблону и содержит минимум:
   - архитектурный документ
   - аналитический документ уровня PRD/feature-spec
   - implementation-статус
   - QA-чеклист
3. Каждая новая фича должна быть зарегистрирована в `docs/features/CATALOG.md`, чтобы оставаться в общем scope проекта.
4. Порядок прохождения этапов внутри feature packet обязателен:
   - архитектор
   - аналитик
   - разработчик
   - тестировщик
5. Реализация фичи до завершения архитектурного и аналитического этапов считается отклонением от процесса и должна быть отдельно зафиксирована.
6. Пока одна фича находится в разработке, другие фичи могут параллельно находиться на этапах архитектуры или аналитики.
7. Каждый ролевой этап для новой фичи должен выполняться в отдельном окне или треде, чтобы не смешивался контекст ролей.

## Governance
1. Конституция имеет приоритет над локальными ad-hoc решениями.
2. Любое исключение из принципов документируется с явным обоснованием.
3. Контекст проекта поддерживается в `.specify/memory/project-context.md`.
