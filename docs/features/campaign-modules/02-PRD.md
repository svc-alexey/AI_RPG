# PRD: Campaign Modules

## 1. Контекст

Перед началом изучить:

- [PRD.md](D:/AI_PRG/PRD.md)
- [ImplementationPlan.md](D:/AI_PRG/ImplementationPlan.md)
- [docs/features/engine-mechanics-token-control/02-PRD.md](D:/AI_PRG/docs/features/engine-mechanics-token-control/02-PRD.md)
- [.specify/memory/project-context.md](D:/AI_PRG/.specify/memory/project-context.md)

Сейчас продукт уже умеет хранить кампанию, инвентарь, часть боевого состояния и summary, но модель остаётся слишком жёсткой для разных типов историй. Пользователь может запускать:

- fantasy RPG с HP, ресурсами и спутниками;
- detective-story, где важнее улики, заметки и отношения;
- sci-fi сценарий с кредитами, репутацией, доступами, модификациями;
- чисто narrative campaign, где вообще не нужны ни золото, ни уровень, ни combat-loop.

Если UI и state по умолчанию навязывают всем кампаниям одни и те же RPG-поля, это создаёт шум, портит immersion и усложняет архитектуру.

## 2. Цель пользователя

Игрок хочет, чтобы игра подстраивалась под конкретную историю:

- показывала только те системы, которые реально участвуют в кампании;
- умела распознать, что история требует предметов, спутников, здоровья, улик, валюты или прогрессии;
- подключала новые системы по мере развития сюжета;
- ненавязчиво сообщала о важных изменениях состояния;
- сохраняла всё это как structured local state, а не как случайный текст в narration.

## 3. Пользовательские сценарии

### Сценарий 1. Детектив без лишнего RPG-интерфейса

Игрок запускает detective-кампанию. На старте активны только `Core`, `Notes` и, при необходимости, `Inventory`. В интерфейсе нет `Gold`, `EXP`, `Level`, боевых панелей и лишних чисел. В sidebar показываются только улики, заметки и текущая цель.

### Сценарий 2. Fantasy-кампания с богатой системой

Игрок запускает fantasy-кампанию. На старте активны `Inventory`, `Vitality`, `Notes`, а `Companions` и `Progression` могут включиться сразу или по мере истории. UI показывает соответствующие панели и state chips.

### Сценарий 3. Prompt сразу задаёт дополнительный модуль

Игрок пишет story wish в духе "хочу партийное путешествие с наёмниками и управлением припасами". На этапе создания игры система рекомендует активировать `Companions` и `Resources`, даже если сеттинг сам по себе этого не требовал.

### Сценарий 4. Модуль подключается по ходу истории

В изначально narrative-heavy истории герой получает постоянного спутника. После turn reconciliation система активирует `Companions`, создаёт первую запись и мягко показывает уведомление "Новый модуль: Спутники" и "К вам присоединился Райн".

### Сценарий 5. Игрок получает ненавязчивые уведомления

После хода игрок видит маленькое полупрозрачное окно на пару секунд:

- `+ Железный ключ`
- `-2 HP`
- `+ 15 кредитов`
- `Спутник: Мара присоединилась`

Окно не блокирует ввод и не уводит фокус от чата.

### Сценарий 6. Детали доступны в sidebar

После краткого уведомления игрок может открыть sidebar или drawer и увидеть:

- предметы;
- спутников;
- заметки/улики;
- здоровье и эффекты;
- ресурсы;
- прогрессию.

Но только для тех модулей, которые реально активны в кампании.

### Сценарий 7. Deterministic systems не навязываются всем

Если в истории активировался `Checks` или `Combat` module, локальный движок начинает считать проверки и урон детерминированно. Если модуль не активен, история остаётся более свободной и narrative-driven.

## 4. Функциональные требования

### 4.1 Общая модель модулей

Система должна:

1. Разделить state кампании на:
   - `Core State` - всегда активен;
   - `Optional Modules` - подключаются по необходимости.
2. Хранить список активных модулей как часть кампании.
3. Хранить причину активации модуля:
   - `setting_default`
   - `prompt_inference`
   - `user_selected`
   - `story_unlocked`
   - `migration`
4. Поддерживать soft-disabled состояние для модулей, которые были активны, но временно не отображаются в UI.

### 4.2 Обязательный core state

Core state должен включать:

- campaign metadata;
- setting / mode / difficulty;
- location;
- objective / active goal;
- summary / recent turns;
- message log;
- base identity персонажа.

Core state не должен зависеть от конкретного жанра.

### 4.3 Каталог модулей первого релиза

Система должна поддерживать как минимум:

1. `Inventory`
   - предметы, ключевые объекты, расходники, экипировка.
2. `Companions`
   - спутники, важные союзники, их статус и заметки.
3. `Notes`
   - улики, заметки, world facts, journal entries.
4. `Vitality`
   - `HP`, `energy`, injuries, healing events.
5. `Resources`
   - валюта и счётчики: `gold`, `credits`, `supplies`, `reputation`, `heat`.
6. `Progression`
   - `exp`, `level`, `rank`, milestones.
7. `Checks`
   - skill checks, deterministic rolls, combat-related gates.

### 4.4 Стартовая активация модулей при создании кампании

При создании новой кампании система должна:

1. Иметь preset-набор модулей по `setting`.
2. Учитывать `story wish`, `custom story prompt`, `character prompt`.
3. Формировать рекомендованный список активных модулей до старта кампании.
4. Показывать активные модули в review step создания игры.
5. Позволять пользователю в будущем вручную подтвердить или изменить набор модулей, но первый релиз может ограничиться auto-setup плюс soft transparency в review UI.

### 4.5 Базовые рекомендации по сеттингам

Для первого продукта рекомендуются такие пресеты:

1. `fantasy`
   - default: `Inventory`, `Vitality`, `Notes`
   - optional by prompt: `Companions`, `Resources`, `Progression`, `Checks`
2. `detective`
   - default: `Notes`
   - optional by prompt: `Inventory`, `Companions`, `Vitality`
   - by default не включать `Resources` и `Progression`
3. `sciFi`
   - default: `Inventory`, `Notes`
   - optional by prompt: `Companions`, `Vitality`, `Resources`, `Checks`
   - `Progression` только если история явно системная

### 4.6 Динамическая активация модулей по ходу истории

После каждого завершённого хода система должна уметь:

1. Анализировать narration, structured state changes и extraction hints.
2. Понимать, что история впервые ввела новую системную сущность:
   - постоянный спутник;
   - устойчивую валюту;
   - повторяющийся ресурс;
   - здоровье/урон;
   - формализованную прогрессию;
   - детерминированные проверки.
3. Активировать модуль, если уверенность достаточна и правило безопасно.
4. Избегать ложных срабатываний на одноразовые художественные упоминания.
5. Не активировать high-impact modules слишком агрессивно.

### 4.7 Extraction и reconciliation

`EntityExtractionService` должен:

1. Работать поверх rule-based extraction в первом релизе.
2. Извлекать изменения как нормализованные patch-события:
   - `add_item`
   - `remove_item`
   - `update_item_quantity`
   - `add_companion`
   - `update_companion_status`
   - `add_note`
   - `set_resource`
   - `delta_resource`
   - `delta_hp`
   - `delta_energy`
   - `activate_module`
3. Пропускать patch через reconciliation перед сохранением:
   - dedupe;
   - id normalization;
   - conflict resolution;
   - confidence gating.
4. Мутировать только активные модули, кроме явного `activate_module`.
5. Не писать сомнительные сущности в storage без правил и минимальной уверенности.

### 4.8 Module-aware persistence

Persistence слой должен:

1. Хранить активные модули явно.
2. Хранить module-specific entities раздельно, а не в одном тяжёлом blob.
3. Сохранять причины активации и timestamps для module unlock.
4. Загружать только нужные state slices для UI и prompt assembly.
5. Сохранять совместимость со старыми save через миграцию.

### 4.9 Module-aware context assembly

Context builder должен:

1. Передавать модели только core state и relevant modules.
2. Не отправлять `Gold`, `EXP`, `Level` в историях, где эти модули не активны.
3. Подмешивать в prompt краткий список активных модулей и их правила.
4. Учитывать module-specific notes и counters при summary.

### 4.10 Module-aware UI

Gameplay UI должен:

1. Рендерить sidebar секции только для активных модулей.
2. На mobile показывать эти секции через drawer, tabs, sheets или accordion-паттерн.
3. На desktop использовать левую/правую колонку без перегрузки основного чата.
4. Подсвечивать только что изменившийся модуль мягким highlight.
5. Не ломать главный игровой loop "чат -> действие -> narration".

### 4.11 Уведомления о state changes

Система должна показывать ненавязчивые transient notifications:

1. Формат:
   - небольшая полупрозрачная карточка;
   - поверх чата;
   - без модального затемнения;
   - без блокировки ввода.
2. Поведение:
   - появляется на 2-3 секунды;
   - мягко fade/slide-in;
   - автоматически исчезает;
   - может стековаться максимум по 2 штуки;
   - повторяющиеся изменения одного хода могут группироваться.
3. Типы уведомлений:
   - найден предмет;
   - потерян предмет;
   - изменилось HP/energy;
   - изменился ресурс;
   - присоединился спутник;
   - активирован новый модуль.
4. После исчезновения уведомления детальная информация должна быть доступна в sidebar.
5. Уведомления не должны превращаться в шум при частых изменениях.

### 4.12 Deterministic systems по модулю

Система должна:

1. Включать `DiceEngine` только там, где активен `Checks` module.
2. Ограничивать deterministic combat аналогично.
3. Давать AI narration уже после расчёта исхода, а не до него.
4. Не делать проверки обязательными для narrative-only историй.

### 4.13 Пользовательский контроль и прозрачность

Пользователь должен понимать:

- какие модули сейчас активны;
- почему активировался новый модуль;
- где посмотреть подробности;
- что изменения пришли из истории, а не "из ниоткуда".

Первый релиз может ограничиться прозрачными уведомлениями и read-only отображением причин активации.

## 5. Нефункциональные требования

- **Производительность:** module-aware loading и selective rebuilds; transient notifications не должны вызывать тяжёлые redraw.
- **Локализация:** все названия модулей, причины активации и уведомления должны поддерживать `ru/en`.
- **Надёжность:** ложные извлечения и ложные активации должны быть редкими и обратимыми.
- **Совместимость:** старые save продолжают открываться.
- **Масштабируемость:** новая модульная схема должна позволять добавлять новые modules без полного рефакторинга кампании.
- **UX:** UI не должен навязывать системность там, где история хочет быть свободной.

## 6. Влияние на текущие stage

### Stage 5. Hybrid context

Нужно сделать context builder module-aware, чтобы он посылал только relevant state.

### Stage 6. World state and extraction

Нужно переосмыслить stage как "modular world state and extraction", а не как жёсткое добавление `Gold/Exp/Level`.

### Stage 7. Dice engine and deterministic checks

Нужно делать deterministic systems как opt-in modules, а не universal foundation для всех историй.

### Stage 8. UI expansion

Нужно строить adaptive sidebar и overlay notifications поверх активных модулей, а не проектировать один универсальный RPG-dashboard.

### New Game flow

Нужно добавить module recommendations и обзор активных модулей до старта кампании.

## 7. Definition of Done

1. Кампания хранит явный список активных модулей.
2. Сеттинг и initial prompt влияют на стартовый набор модулей.
3. Система может безопасно активировать новый модуль по ходу истории.
4. Sidebar показывает только активные модули.
5. Игрок получает лёгкие полупрозрачные уведомления о важных изменениях состояния.
6. Extraction и reconciliation работают module-aware.
7. Истории без RPG-экономики больше не показывают ненужные `Gold`, `EXP`, `Level`.
8. `flutter analyze` и релевантные тесты не показывают регрессий после внедрения модульной схемы.
