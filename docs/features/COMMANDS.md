# Commands Protocol

## Общий принцип

Для каждой новой фичи работа идет не только по документам, но и по отдельным окнам работы.

Правило:
- архитектор работает в отдельном окне/треде
- аналитик работает в отдельном окне/треде
- разработчик работает в отдельном окне/треде
- тестировщик работает в отдельном окне/треде

Это нужно, чтобы:
- не смешивался контекст ролей
- было проще возвращаться к решениям по этапам
- каждая роль работала в рамках своей задачи и своих документов

## Автономный режим

Если пользователь формулирует запрос как выполнение фичи целиком, без паузы между этапами, агент обязан:
1. сам добавить или обновить запись в [ImplementationPlan.md](D:/AI_PRG/ImplementationPlan.md)
2. сам зарегистрировать фичу в [docs/features/CATALOG.md](D:/AI_PRG/docs/features/CATALOG.md)
3. сам создать или обновить feature-папку
4. последовательно пройти роли:
   - архитектор
   - аналитик
   - разработчик
   - тестировщик
5. не ждать отдельного подтверждения между этапами, если нет скрытого риска или неоднозначного выбора

Отдельные окна/роли в таком режиме считаются логическими этапами одного автономного исполнения.

## Как запускать новую фичу

1. Создать запись в [ImplementationPlan.md](D:/AI_PRG/ImplementationPlan.md)
2. Создать запись в [docs/features/CATALOG.md](D:/AI_PRG/docs/features/CATALOG.md)
3. Создать git-ветку фичи в формате `codex/<feature-slug>`
4. Создать feature-папку по шаблону `docs/features/_template/`

## Как открывать окна по ролям

### Окно 1. Архитектор
Команда:
`/speckit.specify`

Результат:
- заполнен `01-Architecture.md`
- зафиксированы архитектурные решения, риски и границы

### Окно 2. Аналитик
Команда:
`/speckit.plan`

Результат:
- заполнен `02-PRD.md`
- зафиксированы пользовательские сценарии и требования

### Окно 3. Разработчик
Команда:
`/speckit.tasks`
затем
`/speckit.implement`

Результат:
- заполнен `03-Implementation.md`
- выполнена реализация
- обновлены чекбоксы

### Окно 4. Тестировщик
Команда:
ручной QA-проход + проверки проекта

Результат:
- заполнен `04-QA.md`
- зафиксированы результаты приемки и остаточные риски

## Важное правило

Если одна фича находится в реализации, другие фичи можно параллельно вести, но тоже по отдельным окнам:
- отдельное окно на архитектуру одной фичи
- отдельное окно на аналитику другой фичи
- отдельное окно на разработку третьей фичи

Смешивать несколько ролей в одном окне для новой фичи нельзя, кроме локального bugfix.

## Git Merge Policy

1. Каждая новая фича разрабатывается в отдельной git-ветке формата `codex/<feature-slug>`.
2. Реализация, проверки и feature-документация ведутся внутри этой feature-ветки.
3. Если фича завершена, прошла проверки и готова к приемке, агент обязан слить ее в `master`.
4. После merge в `master` агент обязан повторно прогнать проверки уже на объединенном результате.
5. `master` считается веткой только для стабильного, проверенного состояния проекта.
