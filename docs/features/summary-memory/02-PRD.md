# PRD: Summary Memory

## 1. Контекст

Фича развивает требования из:
- [PRD.md](D:/AI_PRG/PRD.md)
- [ImplementationPlan.md](D:/AI_PRG/ImplementationPlan.md)
- [docs/features/summary-memory/01-Architecture.md](D:/AI_PRG/docs/features/summary-memory/01-Architecture.md)

Цель фичи: обеспечить устойчивую связность кампании при длинной игре и при возобновлении сохранения, не перегружая локальную модель лишним контекстом.

## 2. Проблема пользователя

Игрок должен чувствовать, что игра помнит:
- что уже произошло
- что сейчас важно
- к чему ведет текущая сцена

Сейчас риск такой:
- через несколько ходов AI теряет нить
- после загрузки кампании игра может отвечать менее связно
- локальная модель получает слишком сырой и шумный контекст

## 3. Цель пользователя

Как игрок, я хочу, чтобы после длинной серии ходов и после загрузки сохранения игра продолжала историю последовательно, не забывала текущие цели и не путала факты мира.

Как разработчик продукта, я хочу уменьшить контекстный шум и сделать передачу кампании в AI стабильной и воспроизводимой.

## 4. Пользовательские сценарии

### Сценарий 1. Длинная сессия
Игрок проходит 10+ ходов подряд.
Система должна сохранять причинно-следственную связность сцены и не забывать активную цель.

### Сценарий 2. Возврат к сохранению
Игрок закрывает приложение и позже загружает кампанию.
Игра должна быстро восстановить понятный контекст и продолжить историю без ощущения, что все началось заново.

### Сценарий 3. Локальная модель с ограниченным контекстом
Игрок использует LM Studio.
Система должна отправлять в модель компактный, но достаточный payload, чтобы не провоцировать деградацию качества и лишнюю latency.

### Сценарий 4. Ошибка или сбой AI
Если модель ответила странно или неполно, сохраненная memory-структура не должна ломаться и терять канон кампании.

## 5. Функциональные требования

1. Система должна хранить долгоживущую сводку кампании отдельно от недавних событий.
2. Система должна хранить недавние ходы в компактном формате.
3. Система должна хранить текущую активную цель отдельно от narrative.
4. Система должна собирать AI-context не из полного chat log, а из memory payload.
5. После каждого validated turn система должна обновлять memory-структуру.
6. После загрузки сохранения memory-структура должна быть доступна без дополнительных ручных действий.
7. UI должен показывать полезную сводку кампании в читаемом виде.
8. Система должна ограничивать размер recent context по количеству элементов.
9. Система не должна допускать, чтобы невалидный AI-output напрямую переписывал memory-канон.

## 6. Нефункциональные требования

1. Memory-представление должно быть компактнее полного `CampaignState`.
2. Обновление summary не должно заметно тормозить игровой ход.
3. Структура памяти должна быть сериализуемой и совместимой с save/load.
4. Решение должно работать как с LM Studio, так и с OpenAI-compatible endpoint.
5. Решение должно быть готово к будущему расширению в entity cards и world canon.

## 7. Ограничения

1. В первый этап не входит retrieval или vector search.
2. В первый этап не входит полноценная knowledge base сущностей.
3. Summary не должен становиться единственным источником истины; source of truth остается state + движок.

## 8. Definition of Done

1. В доменной модели кампании появилась отдельная memory-структура, а не только одно поле `summary`.
2. AI-клиент получает structured memory payload вместо полного сырого состояния кампании.
3. После 10+ ходов история остается связной и не теряет активную цель.
4. После загрузки сохранения игрок видит понятную сводку текущего положения.
5. Ошибка AI не ломает memory-канон кампании.
6. Save/load корректно сохраняет и восстанавливает новую memory-структуру.

## 9. Метрики успеха

1. Снижение среднего размера prompt payload для кампании по сравнению с передачей полного сырого состояния.
2. Снижение числа случаев, когда модель теряет активную цель или противоречит недавним событиям.
3. Снижение количества ручных переформулировок от игрока после загрузки save.

## 10. Открытые вопросы для следующего этапа

1. Нужна ли отдельная краткая сводка для UI и отдельная summary-версия для AI?
2. Нужно ли в MVP+ хранить `activeSituation` отдельно от `activeGoal`?
3. Стоит ли пересчитывать rolling summary по таймеру, по числу ходов или только по важным событиям?
