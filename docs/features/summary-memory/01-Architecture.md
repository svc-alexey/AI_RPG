## 2. Проблема текущего состояния

Сейчас у кампании есть только одно поле `summary`, которое фактически хранит последнюю короткую выжимку хода. Это создает несколько архитектурных проблем:
- длинная кампания теряет связность после серии ходов
- в prompt уходит почти полный `CampaignState`, что со временем даст шум и рост latency
- нет разделения между каноном кампании, недавними событиями и активной целью
- при ошибках модели сложно понять, какой кусок контекста действительно был важен

## 3. Цель архитектурного этапа

Построить минимальную, но устойчивую memory-архитектуру, которая:
- сжимает контекст кампании без разрушения игровых фактов
- отделяет долгоживущую память от недавних событий
- уменьшает размер prompt и снижает шанс потери контекста
- не ломает save/load и существующий MVP-цикл

## 4. Предлагаемая архитектура памяти

### 4.1 Слои памяти

Контекст кампании должен собираться из четырех слоев:

1. `core_state`
- краткий структурированный снимок текущего состояния
- персонаж, ресурсы, локация, активная цель, ключевой инвентарь, ключевые флаги
- источник истины: доменная модель кампании

2. `recent_turns`
- последние 3-6 завершенных ходов в компактном виде
- нужен для локальной связности сцены
- хранится отдельно от полного chat log

3. `rolling_summary`
- накапливаемая сводка кампании
- обновляется не каждый токен, а по cadence: например, каждые 3-5 ходов или при достижении важного события
- хранит устойчивые факты и причинно-следственные связи

4. `active_context`
- текущая активная цель
- текущая сцена/угроза
- незавершенные последствия последнего хода
- нужен для immediate continuity

### 4.2 Что не должно идти в prompt целиком

В prompt не должен отправляться весь `messages` log кампании.

Вместо этого:
- полный лог остается в сохранении для UI и аудита
- AI получает только `recent_turns + rolling_summary + active_context + core_state`

### 4.3 Граница между движком и AI

AI не должен быть владельцем памяти.

Правильный поток:
1. движок завершает ход
2. memory builder извлекает факты из validated state
3. memory manager обновляет `recent_turns`, `rolling_summary`, `active_context`
4. AI-клиент получает уже подготовленный memory payload

Это важно, чтобы:
- память обновлялась только после валидированного хода
- галлюцинации модели не становились каноном
- save/load оставался воспроизводимым

## 5. Изменения в моделях данных

### 5.1 В `CampaignState`

Нужно заменить одно поле `summary` на более явную структуру, например:

- `campaignSummary`
- `activeObjective`
- `activeSituation`
- `recentTurns`
- `memoryVersion`

Минимальный вариант для MVP+:
- `summary`: долгоживущая сводка
- `activeGoal`: текущая цель
- `recentTurns`: список компактных turn summaries

### 5.2 Новая доменная модель

Нужна отдельная модель memory payload, условно:

`CampaignMemoryContext`
- `coreStateSnapshot`
- `rollingSummary`
- `activeGoal`
- `activeSituation`
- `recentTurns`

Она нужна затем, чтобы AI-клиент не собирал prompt прямо из сырого `CampaignState`.

## 6. Memory builder / manager

Нужен отдельный сервис, например:

`CampaignMemoryManager`

Ответственность:
- построить compact snapshot для AI
- обновить recent turns после validated turn
- решить, пора ли пересобирать rolling summary
- ограничить размер контекста

### 6.1 Политика сжатия

Предлагаемая политика:
- `recent_turns`: не более 5 элементов
- каждый recent turn хранится как:
  - действие игрока
  - краткий outcome
  - важное изменение state
- `rolling_summary`: 400-900 символов для MVP
- `active_context`: 1-3 коротких поля, не абзац свободного текста

### 6.2 Политика обновления summary

Summary обновляется:
- каждые N ходов
- при смене локации
- при завершении/получении важной цели
- при сильном изменении состава инвентаря или ресурсов

## 7. Интеграция с AI prompt

Вместо передачи в prompt полного `state.toJson()` нужно перейти к сборке структурированного payload:

```json
{
  "core_state": {},
  "active_context": {},
  "rolling_summary": "",
  "recent_turns": []
}
```

Такой payload:
- компактнее
- стабильнее для модели
- проще валидировать и версионировать

## 8. Защита от потери контекста

Чтобы не было глюков и потери фактов:
- `rolling_summary` обновляется только из validated state
- `recent_turns` формируются приложением, а не копируются из AI-текста как есть
- активная цель хранится как отдельное поле, а не только как часть narrative
- ключевые world facts в summary должны быть ограничены только подтвержденными событиями

## 9. Риски и trade-offs

### Риск 1. Слишком агрессивное сжатие
Может потеряться мотивация сцены или причинно-следственная цепочка.

Снижение риска:
- отдельно хранить `active_context`
- не сжимать последние ходы в один абзац слишком рано

### Риск 2. Слишком слабое сжатие
Prompt снова станет слишком тяжелым и шумным.

Снижение риска:
- hard cap на `recent_turns`
- summary cadence вместо постоянного переписывания

### Риск 3. Summary становится новым источником галлюцинаций

Снижение риска:
- summary строится только после validated turn
- критичные факты берутся из state, а не из narration

## 10. Границы реализации

В первый этап реализации входят:
- новая memory-модель
- manager/builder для recent turns и rolling summary
- переход AI prompt на memory payload
- сохранение новой memory-структуры в save/load
- UI-блок summary

Не входят в первый этап:
- retrieval/RAG
- entity cards
- world canon knowledge base
- отдельный векторный поиск

## 11. Архитектурное решение

Рекомендуемое решение:
- внедрить `CampaignMemoryManager`
- перейти от одиночного `summary` к memory payload из нескольких слоев
- перестать отправлять в AI весь `CampaignState`
- использовать `recent_turns + rolling_summary + active_context + core_state`

Это минимальный путь, который снижает потери контекста без перегрузки MVP сложной memory-системой.
