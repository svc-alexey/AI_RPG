# PRD: Оптимизация расхода токенов в AI_PRG + Symmetry

## 1. Обзор инициативы

**Название:** Token Optimization Initiative  
**Продукт:** `AI_PRG` + `Symmetry`  
**Область:** генерация промптов, игровой turn-processing, RAG-контекст, observability usage  
**Цель:** снизить стоимость и латентность AI-вызовов без ухудшения качества повествования, связности кампаний и UX.

Инициатива охватывает весь путь AI-запроса:

1. генерацию story/character prompts;
2. создание кампании;
3. обработку игровых ходов;
4. передачу контекста в модель;
5. сбор и анализ метрик usage.

## 2. Проблема

Система уже умеет ограничивать `max_tokens`, уменьшать context window и частично сжимать контекст, но расход токенов всё ещё зависит от нескольких дорогих факторов:

1. в запросах остаются длинные неизменяемые блоки;
2. часть схемы и инструкций дублируется между слоями;
3. JSON-контекст использует длинные имена полей;
4. RAG и хроники мира могут передавать больше данных, чем реально нужно для одного хода;
5. токеновая телеметрия сохраняется, но пока недостаточно видна для принятия продуктовых решений;
6. retry-механика при token limit может удваивать расход на неудачных ответах.

Следствие:

1. растёт стоимость одного хода;
2. растёт время ответа модели;
3. сложнее предсказать бюджет на long campaigns;
4. сложнее сравнивать модели и провайдеров по эффективности.

## 3. Целевое состояние

После реализации инициативы система должна:

1. отправлять в модель только минимально необходимый контекст на каждый запрос;
2. жёстко разделять immutable prefix и dynamic tail для prompt caching;
3. передавать компактный, нормализованный и дедуплицированный контекст;
4. иметь отдельные бюджеты токенов для разных типов запросов;
5. измерять usage по каждому ключевому сценарию и показывать тренды;
6. сохранять качество нарратива и связность long campaign на приемлемом уровне.

## 4. Цели

### 4.1 Основные цели

1. Снизить средний `prompt_tokens` на один ход кампании.
2. Снизить средний `total_tokens` на один ход кампании.
3. Снизить долю запросов, где происходит повторный вызов из-за `max_tokens`/`length`.
4. Сохранить или улучшить perceived quality нарратива.
5. Сделать расход токенов измеряемым на уровне фичи, сценария и модели.

### 4.2 Вторичные цели

1. Упростить prompt templates.
2. Сделать поведение разных story modes более предсказуемым по бюджету.
3. Упростить будущий переход на более строгую политику cost control.

## 5. Не-цели

1. Полный отказ от rich narration ради экстремальной экономии.
2. Переписывание всей narrative-логики с нуля.
3. Удаление long campaign как режима.
4. Отказ от RAG или world chronicle механики.
5. Оптимизация стоимости embeddings в рамках этой фазы, кроме случаев, когда это прямо влияет на токены LLM.

## 6. Основные сценарии

1. Пользователь генерирует стартовые story/character prompts.
2. Пользователь создаёт новую кампанию.
3. Пользователь запускает intro turn.
4. Пользователь делает обычный игровой ход.
5. Пользователь играет длинную кампанию, где важно удерживать связность без распухания контекста.
6. Разработчик сравнивает расход токенов между моделями, story modes и типами запросов.

## 7. Текущее состояние реализации

Уже реализовано:

1. Ограничение `maxResponseTokens` и `contextWindowSize` через пресеты `cheap`, `fast`, `smart`.
2. Частичное сжатие контекста в клиентской сборке памяти:
   - trim и схлопывание пробелов;
   - ограничение recent turns;
   - shrink по размеру контекста.
3. Stable prefix / dynamic tail логика в backend для turn processing.
4. Сохранение `prompt_cache_hit_tokens`, `prompt_cache_miss_tokens`, `prompt_tokens`, `completion_tokens`, `total_tokens`.
5. Разделение bootstrap/dynamic данных в серверном turn context.
6. RAG-поиск по `world_chronicles`.

Ограничения текущего состояния:

1. usage-метрики есть, но не оформлены как продуктовые KPI;
2. часть префикса всё ещё остаётся слишком длинной;
3. длинные JSON-ключи создают лишний расход;
4. retry при token limit может быть слишком дорогим;
5. budgets пока недостаточно дифференцированы по сценарию.

## 8. Продуктовые требования

### 8.1 Prompt budget management

1. Для каждого типа AI-запроса должен быть определён отдельный budget profile:
   - prompt generation;
   - campaign intro;
   - normal turn;
   - suggestions-only;
   - long-campaign major turn.
2. Каждый profile должен задавать:
   - допустимый `context window`;
   - целевой `max_tokens`;
   - правила fallback/retry;
   - допустимый объём RAG-контекста.
3. Система не должна использовать один и тот же budget по умолчанию для всех AI-операций.

### 8.2 Prompt deduplication

1. Неизменяемые данные кампании должны максимально передаваться как стабильный prefix.
2. На каждый ход в динамическую часть должны попадать только:
   - свежий player action;
   - актуальное краткое состояние;
   - небольшой recent buffer;
   - минимально нужный RAG-tail.
3. Дублирующие инструкции между system prompt, schema prompt и user payload должны быть устранены.

### 8.3 Context compaction

1. Все пользовательские текстовые поля должны нормализоваться:
   - `trim`;
   - схлопывание повторных пробелов;
   - схлопывание лишних переносов строк.
2. Контекст должен храниться и передаваться в краткой форме, где это безопасно:
   - короткие ключи или компактная схема;
   - summary вместо сырого длинного текста;
   - ограничение длины narrative memories и chronicle fragments.
3. В prompt не должны попадать поля, которые не влияют на ответ модели в текущем сценарии.

### 8.4 RAG budget control

1. RAG должен ограничиваться не только `top_k`, но и общим текстовым бюджетом.
2. Каждая хроника должна передаваться в модель в компактной форме.
3. В prompt не должна уходить тяжёлая `metadata`, если она не используется моделью.
4. Для shortStory RAG budget должен быть заметно ниже, чем для longCampaign.

### 8.5 Retry and fallback policy

1. Retry после token limit должен быть ограничен понятными правилами.
2. Повторный запрос с увеличенным `max_tokens` должен выполняться только в сценариях, где это оправдано:
   - intro turn;
   - longCampaign;
   - важные нарративные ходы.
3. Для дешёвых и коротких сценариев система должна предпочитать компактный fallback, а не дорогой retry.

### 8.6 Observability and analytics

1. Для каждого AI-запроса должны быть доступны:
   - `prompt_tokens`;
   - `completion_tokens`;
   - `total_tokens`;
   - `prompt_cache_hit_tokens`;
   - `prompt_cache_miss_tokens`;
   - тип сценария;
   - story mode;
   - модель;
   - success/fallback/retry outcome.
2. Должны быть агрегированные метрики:
   - средний расход токенов на prompt generation;
   - средний расход токенов на normal turn;
   - средний расход токенов на intro turn;
   - cache hit ratio;
   - retry rate;
   - token-limit rate.
3. Команда должна иметь возможность сравнить расход токенов до и после оптимизаций.

## 9. Нефункциональные требования

1. Оптимизация токенов не должна ломать существующую игровую семантику.
2. Качество longCampaign не должно заметно деградировать из-за чрезмерного сжатия.
3. Изменения должны быть совместимы с OpenAI-compatible провайдерами.
4. Архитектура должна позволять дальнейшую настройку budgets без крупных рефакторингов.
5. Usage logging не должен раскрывать пользовательские секреты и приватные credentials.

## 10. Требования к качеству нарратива

После оптимизаций система должна сохранять:

1. понятную и связную сцену на каждом ходе;
2. корректную continuity между recent turns;
3. адекватное использование location/objective;
4. внятные и короткие choices;
5. достаточно богатый intro для `longCampaign`.

Допустимые компромиссы:

1. меньше декоративных сенсорных деталей в shortStory;
2. более короткая memory_entry;
3. более компактные objective/quest notes;
4. более строгий budget для suggestions-only режима.

## 11. Метрики успеха

### 11.1 KPI

1. Снижение среднего `prompt_tokens` на normal turn минимум на `20%`.
2. Снижение среднего `total_tokens` на normal turn минимум на `15%`.
3. Снижение token-limit retry rate минимум на `30%`.
4. Рост доли cache-hit токенов в turn-processing запросах.
5. Отсутствие статистически заметного роста ошибок качества по ручной QA-оценке.

### 11.2 Guardrails

1. Не должно быть роста provider invalid response rate.
2. Не должно быть роста user-facing turn failures.
3. Не должно быть заметного ухудшения intro quality у `longCampaign`.
4. Не должно быть ухудшения world continuity в QA-сценариях.

## 12. Этапы реализации

### Этап 1. Измеримость и baseline

1. Зафиксировать baseline по usage для prompt generation, intro, normal turn и long campaign.
2. Добавить удобную агрегацию usage по типу запроса.
3. Ввести dashboard или выгрузку для сравнения до/после.

**Результат:** команда знает, где основной перерасход и какие сценарии самые дорогие.

### Этап 2. Сжатие структуры prompt

1. Укоротить канонический system/schema prompt.
2. Устранить дубли инструкций между слоями.
3. Сократить имена JSON-ключей там, где это безопасно.
4. Удалить неиспользуемые поля из dynamic context.

**Результат:** уменьшается постоянная цена каждого запроса.

### Этап 3. Сжатие payload и RAG

1. Ограничить RAG общим текстовым budget.
2. Передавать в модель summary хроник вместо тяжёлых записей.
3. Ужесточить budgets recent turns и world state по story mode.

**Результат:** уменьшается переменная цена хода.

### Этап 4. Budget profiles и retry policy

1. Ввести разные budgets по сценарию.
2. Ограничить дорогие retry.
3. Добавить fallback policy для коротких сценариев.

**Результат:** система тратит токены более предсказуемо и реже уходит в двойную стоимость.

### Этап 5. QA и rollout

1. Сравнить usage до/после.
2. Прогнать narrative QA по shortStory и longCampaign.
3. Включить оптимизации поэтапно.

**Результат:** изменения доказуемо экономят токены без регрессий качества.

## 13. Приоритеты

### P0

1. Baseline usage и аналитика.
2. Budget profiles по типам запросов.
3. Сжатие длинных и дублирующихся prompt-блоков.

### P1

1. RAG text budget.
2. Сокращение JSON-ключей и payload normalization.
3. Ограничение retry по token-limit.

### P2

1. Более агрессивные режимы cheap/fast.
2. Тонкая story-mode настройка budgets.
3. Автоматический quality-vs-cost benchmarking между моделями.

## 14. Риски

1. Слишком агрессивное сжатие может ухудшить narration quality.
2. Укорачивание schema prompt может увеличить риск invalid JSON.
3. Слишком маленький RAG budget может ухудшить continuity мира.
4. Разные провайдеры могут по-разному реагировать на компактные prompts.
5. Укороченные ключи могут ухудшить читаемость внутренней отладки.

## 15. Митигации

1. Внедрять оптимизации поэтапно и сравнивать usage до/после.
2. Оставить narrative QA на shortStory и longCampaign.
3. Сохранять fallback parser/validator для structured output.
4. Ввести feature flags или конфигурационные профили для rollout.
5. Хранить читаемую внутреннюю модель данных, а сокращать только внешний LLM payload.

## 16. Definition of Done

Инициатива считается завершённой, когда:

1. есть зафиксированный baseline и post-change usage report;
2. normal turn и intro turn используют отдельные budget profiles;
3. prompt и context стали компактнее и без очевидных дублей;
4. RAG ограничен не только по количеству записей, но и по текстовому объёму;
5. retry-policy по token limit стала управляемой;
6. usage-метрики доступны для анализа по сценариям;
7. QA подтверждает, что shortStory и longCampaign остаются играбельными и связными.

## 17. Следующие артефакты после PRD

После утверждения этого PRD должны появиться:

1. технический implementation plan по backend и Flutter;
2. список конкретных изменений prompt/schema/context;
3. baseline report по usage;
4. QA checklist по narrative quality;
5. rollout plan с флагами или стадиями включения.
