# PRD: AI_PRG + Symmetry

## 1. Обзор продукта

**Название:** AI_PRG  
**Тип:** narrative RPG с серверной обработкой кампаний, живым миром и AI-повествованием  
**Клиент:** Flutter  
**Backend:** `Symmetry` на `FastAPI`  
**Ключевой принцип:** модель пишет повествование, но источником истины остаётся серверная игровая логика и сохранённое состояние мира.

## 2. Целевое состояние продукта

1. Пользователь входит в аккаунт и играет через серверную кампанию.
2. Кампания, мир, память и история ходов хранятся на сервере.
3. Сервер делает RAG по векторной памяти и симулирует живой мир.
4. Flutter отвечает за UX, ввод и отображение, а не за authoritative state.
5. Пользователь может использовать:
   - серверные AI-креды по умолчанию;
   - свои AI-креды, но без хранения на сервере.

## 3. Цели текущей версии

1. Перевести игру на server-first архитектуру.
2. Поддержать регистрацию, логин, refresh/logout и серверные сессии.
3. Реализовать серверную обработку хода:
   - загрузка snapshot-а;
   - RAG;
   - вызов модели;
   - применение состояния;
   - сохранение нового snapshot-а.
4. Поддержать живой мир через `world_state` и `world_chronicles`.
5. Заложить story library в backend и API.
6. Подготовить БД и rollout к будущему переносу на сервер.

## 4. Не-цели текущей версии

1. Полноценный multiplayer.
2. Реальные платежи и прод-биллинг.
3. UI для story library в Flutter.
4. Полностью проверенный production Yandex OAuth flow с живыми credentials.
5. Сложная moderation layer для пользовательского контента.

## 5. Целевая аудитория

1. Игроки narrative RPG, которым нужен стабильный аккаунт и серверные кампании.
2. Пользователи, которые хотят играть на серверных моделях или со своими ключами.
3. Автор продукта, которому нужен перенос разработки 1:1 с локального окружения на сервер.

## 6. Основные пользовательские сценарии

1. Пользователь запускает приложение, входит по email/password и создаёт кампанию.
2. Пользователь делает ход, а сервер возвращает уже сохранённый и применённый результат.
3. Пользователь закрывает приложение и позже продолжает ту же кампанию с сервера.
4. Пользователь вводит свои API-ключи в приложении, и backend использует их только на время конкретного запроса.
5. Пользователь публикует story template или работает с уже созданными шаблонами через backend API.

## 7. Функциональные требования

### 7.1 Авторизация

1. Email auth через `email + password`.
2. Пароли хранятся только как безопасные хэши.
3. Поддерживаются `access token` и `refresh token`.
4. Должен быть logout с отзывом refresh session.
5. Должен быть задел под Yandex OAuth.

### 7.2 Кампании

1. Пользователь может создать кампанию.
2. Пользователь может получить список своих кампаний.
3. Пользователь может открыть текущее состояние кампании.
4. Пользователь может удалить кампанию.
5. Пользователь может обработать игровой ход через серверный API.

### 7.3 Игровой ход

1. Flutter отправляет `campaign_id`, `player_action`, язык и служебные метаданные.
2. Backend загружает текущий snapshot и world state.
3. Backend выполняет RAG-поиск по `world_chronicles`.
4. Backend формирует контекст и вызывает внешнюю модель.
5. Backend валидирует результат и применяет state changes через runtime logic.
6. Backend сохраняет turn, snapshot и update мира.
7. Важные события пишутся в `world_chronicles` фоном.

### 7.4 AI-доступ

1. Backend должен поддерживать серверные креды из `.env`.
2. Backend должен поддерживать пользовательские provider credentials в теле запроса.
3. Пользовательские credentials не должны сохраняться в БД, логах, snapshot-ах или background jobs.
4. AI gateway должен быть OpenAI-compatible.
5. Flutter не должен вызывать внешнего AI-провайдера напрямую в основном игровом цикле.

### 7.5 Story library

1. Backend хранит шаблоны историй.
2. Поддерживаются теги, лайки, просмотры, закладки.
3. Поддерживаются public/private шаблоны.
4. Должны быть фильтрация по тегам и сортировки по `new`, `popular`, `liked`, `viewed`.
5. UI для библиотеки историй пока не обязателен.

### 7.6 Живой мир и память

1. `world_state` хранит механическое состояние мира.
2. `world_chronicles` хранит векторную смысловую память.
3. Векторная память использует фиксированную размерность `1024`.
4. Backend должен отбирать важные события для записи в память.

## 8. Нефункциональные требования

1. Система должна быть оптимизирована для локальной разработки и будущего переноса на сервер.
2. Схема БД должна изменяться только через миграции.
3. AI output считается недоверенным до валидации.
4. Ошибки провайдера не должны повреждать кампанию.
5. Пользовательские секреты не должны утекать в persistence или logs.
6. Архитектура должна оставаться пригодной для desktop, web, Android и iOS клиента.

## 9. Текущее состояние реализации

Уже реализовано:

1. `Symmetry` backend на `FastAPI`.
2. `PostgreSQL + pgvector` через `docker-compose`.
3. Alembic migrations и startup rollout.
4. Email auth + refresh/logout.
5. Yandex OAuth scaffolding.
6. Серверные campaigns API.
7. Серверный turn-processing flow.
8. Локальные embeddings на backend.
9. Story library backend/API foundation.
10. Flutter auth gate и server-first campaign flow.
11. Полное удаление legacy local campaign persistence из runtime-кода.

## 10. Definition of Done для текущей фазы

1. Пользователь может зарегистрироваться и войти.
2. Пользователь может создать кампанию и пройти минимум один полный ход через backend.
3. Кампания загружается и продолжается с сервера.
4. Важное событие сохраняется в `world_chronicles`.
5. User-supplied provider credentials не сохраняются на сервере.
6. Story-template API работает без Flutter UI.
7. Локальная разработка повторяет продовый сценарий: backend + БД локально, а не отдельный offline mode.
