# PRD: AI RPG Platform

## 1. Обзор продукта

**Название:** AI RPG Platform  
**Тип:** narrative RPG с AI-повествованием и детерминированным игровым состоянием  
**Платформа:** Flutter, **mobile-first** UX; целевые сборки включают web, мобильные и desktop-платформы.  
**Ключевой принцип:** LLM генерирует повествование и варианты действий, но источником истины остается игровой state и движок.

## 2. Цели MVP

1. Дать игроку быстрый вход в одиночную narrative RPG-сессию.
2. Поддержать создание кампании с выбором сеттинга, режима и сложности.
3. Реализовать цикл `сцена -> действие игрока -> ответ AI -> валидация -> сохранение состояния`.
4. Поддержать локальные сохранения и продолжение кампании.
5. Поддержать OpenAI-compatible endpoint и локальный LM Studio.
6. Сделать приложение русским по умолчанию с полноценным режимом `en`.

## 3. Не-цели MVP

1. Мультиплеер.
2. Полноценная backend-инфраструктура.
3. Большая экономическая мета-система между кампаниями.
4. Полный RAG-слой с векторным поиском.
5. Генерация картинок, карт и сложного визуального контента как обязательная часть MVP.

## 4. Целевая аудитория

1. Игроки, которым нужен быстрый narrative RPG-опыт.
2. Пользователи локальных LLM через LM Studio.
3. Разработчики и AI-энтузиасты, которым важен controllable игровой state.

## 5. Основные пользовательские сценарии

1. Пользователь запускает приложение, создает новую кампанию и сразу попадает в чат игры.
2. Пользователь настраивает LM Studio или другой OpenAI-compatible endpoint и играет через свою локальную модель.
3. Пользователь сохраняет кампанию и позже продолжает ее без потери ключевого контекста.
4. Пользователь меняет язык интерфейса между `ru` и `en`, и язык меняется и в UI, и в AI-слое.

## 6. Функциональные требования

### 6.1 Создание кампании

1. Пользователь может выбрать сеттинг: `fantasy`, `detective`, `sci-fi`.
2. Пользователь может выбрать режим: `short story`, `long campaign`.
3. Пользователь может выбрать сложность: `easy`, `medium`, `hardcore`.
4. Пользователь может задать имя героя.
5. После создания кампании приложение формирует стартовый `CampaignState`.

### 6.2 Игровой цикл

1. Пользователь вводит действие героя в чат.
2. Приложение отправляет structured request в AI-слой.
3. AI возвращает строго структурированный ответ.
4. Движок валидирует изменения состояния.
5. Приложение сохраняет ход и обновляет UI.
6. Если AI вернул невалидный ответ, состояние игры не должно ломаться.

### 6.3 Память кампании

1. Кампания должна хранить rolling summary.
2. Кампания должна хранить активную цель.
3. Кампания должна хранить recent turns.
4. AI должен получать компактный structured context, а не только сырой лог сообщений.

### 6.4 Настройки AI

1. Пользователь может выбрать AI provider.
2. Пользователь может настроить `baseUrl`, `model`, `apiKey`, timeout.
3. Для LM Studio по умолчанию используется `http://127.0.0.1:1234/v1`.
4. Приложение должно уметь автоматически подбирать загруженную модель LM Studio, если local server запущен.
5. Для LM Studio должен быть доступен быстрый режим через `/no_think` с fallback.

### 6.5 Локализация

1. Приложение по умолчанию стартует на русском языке.
2. Обязателен второй полный язык: английский.
3. Локализация должна охватывать UI, системные сообщения, demo/fallback тексты и AI prompt layer.

### 6.6 Сохранения

1. Приложение должно поддерживать локальные сохранения кампаний.
2. Пользователь должен видеть список сохранений и открывать кампанию повторно.
3. Формат сохранений должен оставаться обратно совместимым в пределах разумной эволюции MVP.
4. Данные **локальны для каждой установки** (web / телефон / ПК); **синхронизация между устройствами** в MVP не входит.
5. До релиза в прод допускается упрощённая политика миграций (без обязательного переноса из устаревших локальных форматов).

## 7. Нефункциональные требования

1. AI output считается недоверенным до валидации.
2. Приложение должно соблюдать **mobile-first**: приоритет узких экранов и одной руки; desktop поддерживается через адаптивную вёрстку.
3. Локальная игра через LM Studio должна работать офлайн после запуска локального сервера модели.
4. Изменения состояния игры не должны применяться по свободному тексту без structured parsing.
5. Ошибки AI не должны приводить к потере save или порче состояния кампании.

## 8. Текущее состояние MVP

На текущий момент уже реализовано:

1. Flutter-каркас с mobile-first адаптивностью.
2. Экраны `Home`, `New Game`, `Chat`, `Settings`, `Saves`.
3. Создание кампании.
4. Один полный AI-driven игровой ход.
5. Локальные сохранения.
6. Интеграция с LM Studio через OpenAI-compatible API.
7. Автоподбор модели LM Studio.
8. Быстрый режим `/no_think` для LM Studio с fallback.
9. Локализация `ru/en`.
10. Summary/memory слой кампании.

## 9. Post-MVP этапы

1. Приведение документации и project context в чистый UTF-8.
2. Quality pass и стабилизация.
3. Расширение memory/model contract при необходимости.
4. Следующий продуктовый слой после стабилизации.

## 10. Definition of Done для MVP

1. Пользователь может создать кампанию и пройти минимум один полный игровой цикл.
2. Пользователь может сохранить и снова открыть кампанию.
3. AI-ответ безопасно обрабатывается даже при ошибке формата.
4. LM Studio работает как минимум через локальный OpenAI-compatible endpoint.
5. Приложение доступно в режимах `ru` и `en`.
