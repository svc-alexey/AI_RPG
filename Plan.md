# План MVP: AI RPG Desktop

## 1. Цель первой итерации

Собрать минимально рабочий desktop MVP на Flutter, в котором игрок может:

1. Создать новую короткую кампанию.
2. Выбрать базовые параметры игры.
3. Общаться с игровым миром через простой чат.
4. Получать AI-ответ в структурированном виде.
5. Сохранять и загружать локальный прогресс.
6. Подключать локальную модель через LM Studio.

Это не "полноценная RPG", а вертикальный срез основного цикла:

`настройка кампании -> старт сцены -> сообщение игрока -> ответ AI -> обновление состояния -> сохранение`

## 2. Что входит в базовый MVP

### 2.1 Пользовательский сценарий

1. Пользователь открывает приложение.
2. Создает новую игру с минимальными настройками:
   - сеттинг
   - режим истории
   - сложность
   - имя героя
3. Попадает на экран чата.
4. Видит стартовое вступление.
5. Отправляет действие текстом.
6. Получает:
   - narration
   - choices
   - изменения состояния
7. Может сохранить игру и позже продолжить.

### 2.2 Минимальные экраны

1. `Home`
   - новая игра
   - продолжить игру
   - настройки
2. `New Game`
   - выбор сеттинга
   - выбор режима
   - выбор сложности
   - имя персонажа
3. `Game Chat`
   - история сообщений
   - поле ввода
   - кнопка отправки
   - кнопка "варианты действий"
   - короткий блок состояния героя
4. `Settings`
   - выбор AI provider
   - base URL
   - model
   - API key при необходимости
   - timeout
   - кнопка "Проверить подключение"
5. `Saves`
   - список локальных сохранений
   - загрузка
   - удаление

### 2.3 Минимальные игровые данные

Для первой версии достаточно:

1. Один стартовый world state:
   - текущая сцена
   - текущая локация
   - номер хода
2. Один персонаж:
   - имя
   - hp
   - энергия
   - 2-3 базовых атрибута
3. Один простой инвентарь:
   - список предметов без сложной экипировки
4. Один простой журнал:
   - текущая цель
   - последние события

## 3. Что сознательно не делаем сейчас

Чтобы MVP не расползся, пока не включаем:

1. Мультиплеер.
2. Генерацию картинок и карт.
3. Сложную систему фракций.
4. RAG и векторную память.
5. Облачные сохранения.
6. Встроенный backend.
7. Несколько AI-провайдеров сверх OpenAI-compatible и LM Studio.

## 4. Архитектура MVP

### 4.1 Основные модули

1. `app`
   - роутинг
   - темы
   - dependency setup
2. `features/game_setup`
   - создание кампании
   - стартовые параметры
3. `features/chat`
   - чат-экран
   - отправка хода
   - отображение narration и choices
4. `features/settings`
   - экран AI-настроек
   - тест подключения
5. `features/saves`
   - список и восстановление сохранений
6. `core/ai`
   - интерфейс провайдера
   - OpenAI-compatible client
   - LM Studio adapter
7. `core/game_engine`
   - состояние кампании
   - валидация AI-ответа
   - применение delta
8. `core/storage`
   - локальное хранение настроек
   - локальное хранение сохранений

### 4.2 Базовый контракт AI

На первом этапе требуем от модели строгий JSON вида:

```json
{
  "narration": "string",
  "choices": ["string"],
  "state_changes": {
    "hp_delta": 0,
    "energy_delta": 0,
    "inventory_add": [],
    "inventory_remove": [],
    "quest_note": "string"
  },
  "memory_entry": "string"
}
```

Если JSON невалиден, используем безопасный fallback:

1. Показать техническое сообщение в чате.
2. Не менять состояние игры.
3. Сохранить сырой ответ в лог для отладки.

### 4.3 Принцип работы движка

LLM не владеет состоянием напрямую.

Поток одного хода:

1. Берем текущий state.
2. Собираем prompt из:
   - правил мира
   - краткого summary
   - текущей сцены
   - сообщения игрока
3. Получаем JSON.
4. Валидируем допустимые изменения.
5. Применяем только разрешенные изменения.
6. Обновляем лог кампании и save.

## 5. LM Studio интеграция

### 5.1 Минимальная поддержка

Достаточно считать LM Studio OpenAI-compatible endpoint.

Поддерживаем в настройках:

1. `provider = lm_studio`
2. `baseUrl`
   - по умолчанию `http://127.0.0.1:1234/v1`
3. `model`
4. `apiKey`
   - опционально, если локальный endpoint не требует ключ
5. `timeoutSeconds`

### 5.2 Проверка подключения

На экране настроек:

1. пользователь сохраняет конфиг;
2. жмет `Проверить подключение`;
3. приложение делает тестовый запрос;
4. показывает один из статусов:
   - подключение успешно
   - endpoint недоступен
   - модель не указана
   - ответ не соответствует формату

### 5.3 Что считаем готовым по LM Studio

1. Приложение может отправить тестовый запрос на локальный endpoint.
2. Приложение может начать кампанию, используя LM Studio как активного провайдера.
3. Один игровой ход проходит до конца без ручной правки JSON.

## 6. Пошаговый план реализации

### Этап 1. Каркас Flutter-приложения

Результат:

1. Создан проект desktop-first на Flutter.
2. Настроена базовая структура папок.
3. Подключены зависимости для state management, HTTP и локального хранения.
4. Есть маршруты на `Home`, `New Game`, `Game Chat`, `Settings`, `Saves`.

### Этап 2. Базовые настройки и конфиг провайдера

Результат:

1. Реализован экран настроек.
2. Настройки сохраняются локально.
3. Есть модель конфигурации AI-провайдера.
4. Реализован сервис проверки подключения.

### Этап 3. Минимальное создание кампании

Результат:

1. Реализован экран `New Game`.
2. Создается стартовый `CampaignState`.
3. Запускается начальная сцена.
4. Можно перейти на экран чата с новым сохранением.

### Этап 4. Чат и игровой цикл

Результат:

1. Пользователь отправляет текст действия.
2. Формируется запрос в AI provider.
3. Ответ отображается в чате.
4. Применяются допустимые изменения состояния.
5. Виден короткий статус героя и последние choices.

### Этап 5. Save/Load

Результат:

1. Каждая кампания хранится локально как отдельный save.
2. Можно продолжить игру после перезапуска приложения.
3. Есть безопасная загрузка схемы данных.

### Этап 6. Полировка MVP

Результат:

1. Добавлен fallback при невалидном JSON.
2. Добавлены загрузочные и error states.
3. Добавлен минимальный summary последних ходов.
4. Описаны ограничения первой версии в UI и документации.

## 7. Очередность задач для ближайшей реализации

Если идти самым коротким путем, делаем в таком порядке:

1. Создать Flutter-проект и базовую структуру модулей.
2. Сделать `Settings` и локальное хранение AI-конфига.
3. Поднять OpenAI-compatible client с поддержкой LM Studio base URL.
4. Сделать `New Game` и стартовый `CampaignState`.
5. Сделать экран чата.
6. Подключить один полный игровой ход через AI.
7. Добавить локальные сохранения.
8. Добавить обработку ошибок и тест подключения.

## 8. Definition of Done для MVP

MVP считаем готовым, когда:

1. Desktop-приложение запускается локально.
2. Пользователь может создать новую короткую игру.
3. Пользователь может подключить LM Studio через настройки.
4. Один и тот же UI работает минимум с OpenAI-compatible endpoint и LM Studio.
5. Игрок может сделать несколько ходов подряд через чат.
6. Состояние героя меняется только через валидируемую delta-модель.
7. Сохранение и загрузка реально восстанавливают кампанию.
8. При плохом ответе модели приложение не ломает save и не падает.
